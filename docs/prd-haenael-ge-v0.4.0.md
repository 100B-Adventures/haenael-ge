## ⓥ v0.3.0 → v0.4.0 변경 요약 (3줄)

1. **로그인 provider 결정**: 카카오 인증 경로는 운영한다. 구글·애플·네이버 소셜 버튼은 앱 출시 시점까지 숨긴다. 구글 코드는 보존하지만 현재 활성 기능으로 간주하지 않는다. (§10.1)
2. **알림톡 도달 경로 운영 반영**: 카카오 비즈앱·`phone_number` scope·`member.phone`·환전 알림톡 2종이 운영에 반영됐다. **단 "로그인 확대"와 "알림 도달"은 별개 축**이며, 전화번호가 없는 사용자는 INAPP 폴백을 쓴다. (§10.2)
3. **환전 신청 신원 정책 현행화**: PASS 완료 기록은 환전 **신청 선행조건이 아니다**. KYC 기록이 없는 가입자도 신청할 수 있고, 최신 확인 결과가 미성년(`is_adult=false`)인 계정만 차단한다. 주민등록번호는 실제 지급 단계에서 수집한다. 로그인·알림에는 PASS를 붙이지 않는다. (§10.3)

## 0. 이 문서가 존재하는 이유

### 0.1 근본 원인 — 결정 A가 하루 만에 뒤집힌 사고

2026-07-20 "1계정 1활성목표"(결정 A)가 마이그레이션 2개(`20260720000000`, `20260720030000`)로 DB에 박혔고, 2026-07-21 회장이 "기존 해낼게 유지하면서 새 목표를 만들고 싶다"로 **뒤집었다.**

- **근본 원인**: 결정 A의 *제품 근거*가 코드·문서 어디에도 없다. 마이그레이션 주석은 "회장 결정 A"라고만 적혀 있고(`20260720000000_goal_one_active_per_member.sql:2`), PRD·user-flow·architecture 어디에도 "왜 1개인가"가 없다. 근거 없는 결정은 반박 불가능하므로 **검증 없이 박히고, 검증 없이 뒤집힌다.**
- **재발 방지 규칙(본 문서 전체에 적용)**: v0.3.0의 **모든 결정에 `근거:` 한 줄을 붙인다.** 근거를 못 쓰는 결정은 결정이 아니라 §9 회수 항목으로 내린다.
- **데이터 복구 논점 종결**: 결정 A 정리 과정에서 소프트삭제된 중복 목표는 **전량 회장 테스트 데이터**임이 마이그레이션 주석에 기록돼 있다 — *"전량 회장 테스트 데이터 — 실사용자 없음"*(`20260720030000_dedup_goal_and_clover_backfill.sql:8`). 또한 처리 방식이 `status='DELETED' + deleted_at=now()` **소프트삭제**라 행 자체는 남아 있다. → **복구 불필요. 이 논점은 여기서 닫는다.**

## 2. F-A. 목표 공개범위 `visibility` enum

### 2.0 용어 고정 (원칙 1)

| 용어 | 정의 | 값 |
|---|---|---|
| **visibility** | *목표 문서 자체*에 누가 접근할 수 있는가 (goal 행 단위) | `PRIVATE` / `FRIENDS` / `PUBLIC` |
| **privacy_flags** | 접근이 허용된 사람에게 *어떤 항목까지* 보이는가 (F-B) | 항목별 3값 |
| **금액 영구비공개** | 개별 응원 금액. **어떤 설정으로도 제3자에게 공개 불가** — 설정 항목이 아니라 **시스템 상수** | (설정 없음) |

> ⚠️ "나만보기"라는 단어는 두 층에서 서로 다른 뜻으로 쓰였다(목표 전체 비공개 vs 응원자 목록 비공개). **이 문서부터 "나만보기"를 UI 라벨로도 금지**하고, `visibility=PRIVATE`(목표 전체) / "친구에게만 보임"(항목별)으로 나눠 부른다. 근거: 원칙 1 위반이 그대로 남으면 RLS 정책명·pgTAP 테스트명까지 오염된다.

### 2.1 사용자 가치
목표를 올렸지만 아직 아무에게도 보이고 싶지 않은 상태(작성 직후·슬럼프 중)에서도 **삭제하지 않고 숨길 수 있다.**
근거: `user-flow.md` §1.2 "계정/목표 삭제"만 있고 "잠시 내리기"가 없어, 부끄러움의 유일한 출구가 삭제였다(공급 이탈 = `docs/risks.md` R10).

### 2.2 입력 / 출력
- **입력**: `visibility ∈ {PRIVATE, FRIENDS, PUBLIC}` (목표 생성 시 기본값 = §9-Q1 회수) + 변경 시각.
- **출력(엔드유저)**: ①소유자 = 목표 카드에 상태 칩("나만 보는 중"/"친구에게 공개"/"링크 아는 사람 모두"). ②링크 방문자 = 접근 가능하면 기존 화면 그대로, 불가하면 "지금은 볼 수 없는 목표예요" + 랜딩 링크(404 아님).

### 2.3 데이터 항목 변경
```
CREATE TYPE goal_visibility_enum AS ENUM ('PRIVATE','FRIENDS','PUBLIC');
ALTER TABLE goal ADD COLUMN visibility goal_visibility_enum NOT NULL DEFAULT 'PUBLIC';
```
- `DEFAULT 'PUBLIC'` = **기존 행 보존 목적의 백필 기본값**(현재 모든 목표가 사실상 링크 공개). 신규 생성 기본값은 애플리케이션이 정한다(§9-Q1).
- `goal_public` 뷰 WHERE 절에 `AND g.visibility = 'PUBLIC'` 추가. **`FRIENDS`는 v2에서 뷰가 서빙하지 않는다** — 친구 관계 테이블이 없기 때문(§2.5).

### 2.4 API 계약 영향
| 대상 | 변경 |
|---|---|
| `goal_public` 뷰 (G2) | WHERE에 visibility 필터 추가. `visibility` **컬럼은 뷰에 넣지 않는다**(제3자에게 "이 사람이 뭘 숨겼는지" 자체가 정보) |
| `goal` insert/update (G1/G4) | `visibility` 필드 추가. RLS `auth.uid()=member_id`로 소유자만 변경 |
| `get_wordmap` RPC (G5) | `SECURITY DEFINER`라 RLS를 우회한다 → **함수 내부에 visibility 체크를 직접 넣어야 한다.** 안 넣으면 PRIVATE 목표의 워드맵이 goalId만 알면 그대로 나온다 (**High 회귀 위험 — 반드시 pgTAP 고정**) |
| `wordmap-render` EF (G6) | service_role이라 동일 위험. 렌더 대상이 PRIVATE면 공유 이미지 생성 거부 |

### 2.5 경계·예외
| 상태 | 처리 |
|---|---|
| PUBLIC → PRIVATE 전환 | 이미 받은 응원·클로버는 **유지**(원장 불변). 링크는 "지금은 볼 수 없는 목표예요"로 전환 |
| PRIVATE 목표에 결제 시도 | `cheer-order` EF가 400 거부. 결제창 진입 전 CTA를 숨기는 것과 **EF 거부 둘 다** 필요(클라만 막으면 우회됨) |
| `FRIENDS` 값의 실제 동작 | ⚠️ **친구 관계 테이블이 없다**(`architecture.md` §4는 `friend_edge`를 "phase2 확장점"으로만 표기). v2에서 `FRIENDS`는 **enum 값만 존재하고 선택 불가(UI 비노출)** — 스키마 옵션을 미리 확보하는 것이 목적. 근거: 회장 지시 "나중 커뮤니티 확장 대비 옵션" + 3값 enum은 나중에 2값→3값 마이그레이션(뷰·RLS·테스트 동시 개정)을 피하게 해준다 |
| 진행 중 결제와 전환 경합 | PENDING 결제가 있는데 PRIVATE 전환 시 → 이미 시작된 결제는 **confirm 허용**(돈은 이미 나갔다). 신규 주문만 차단 |
| 마감(CLOSED) + PRIVATE | 독립 축. 마감은 D-day, visibility는 접근권. 조합 4종 전부 유효 |

### 2.6 측정 가능한 실패 판정
1. anon 키로 `PRIVATE` 목표의 `/g/{slug}` GET → 본문에 title/reason/워드맵 단어가 **1개라도** 노출되면 FAIL.
2. anon 키로 `rpc get_wordmap(PRIVATE goal id)` → 0행이 아니면 FAIL.
3. 기존 PUBLIC 목표 회귀: 마이그레이션 후 `goal_public` 행 수가 마이그레이션 전과 다르면 FAIL.

## 3. F-B. 항목별 프라이버시 설정

### 3.1 회장 정의 확정
"나만보기"의 대상은 **두 항목**이다: ①응원자 **이름 목록** ②응원 **메시지**. 각각에 대해 "제3자에게 보일지 / 친구에게 보일지"를 정한다.
**개별 응원 금액은 어떤 설정으로도 공개 불가 — 영구 본인만.** 근거: 회장 확정 2026-07-21 + `DESIGN.md` §5-1(금액 노출 절대 금지) + 결정 B(§6-b′, 본인 한정) + 이미 적용된 `20260719000000_cheer_amount_privacy.sql`(anon REVOKE).

### 3.2 데이터 항목 변경 (⚠️ 구조 갈림길 → §9-Q2)
필요한 것은 목표당 2개 설정값이다.
```
-- 안 (a) goal 테이블 컬럼 2개  ← 추천
ALTER TABLE goal
  ADD COLUMN supporter_name_visibility goal_visibility_enum NOT NULL DEFAULT 'PUBLIC',
  ADD COLUMN message_visibility        goal_visibility_enum NOT NULL DEFAULT 'PUBLIC';
```
- **추천 근거**: 값 도메인이 visibility와 동일(3값)해서 enum 재사용 → 뷰 조건이 `AND x_visibility='PUBLIC'` 한 줄로 통일된다. jsonb `privacy_flags`(안 b)는 인덱싱·제약·pgTAP 검증이 전부 약해지고, RLS/뷰에서 `->>'x'` 캐스팅이 들어가 실수 표면이 넓어진다.
- **불변식(코드가 아니라 스키마로 박을 것)**: 금액은 컬럼 자체가 공개 표면에 없다. `cheer_public` 뷰에 `clover_amount`·`supporter_ci` **컬럼 부재**가 이미 그 장치다(`20260719000001_cheer_public_view.sql`).

### 3.3 API 계약 영향
- `cheer_public` 뷰(공개 응원자 목록, 아직 화면에 미연결 — `g/[slug]/page.tsx:197` 주석)를 **목표별 설정을 반영하도록 개정**: `display_name`은 `supporter_name_visibility='PUBLIC'`일 때만, `message`는 `message_visibility='PUBLIC'`일 때만 값을 내보내고 아니면 NULL.
- `get_wordmap` RPC: 워드맵은 **메시지 파생물**이다. `message_visibility != 'PUBLIC'`이면 공개 워드맵은 **빈 배열**을 반환해야 한다. → ⚠️ 이는 확산 고리(`user-flow.md` §3)를 끊는다. 트레이드오프는 §9-Q3.

### 3.4 경계·예외
| 상태 | 처리 |
|---|---|
| 메시지 비공개 + 응원자 이름 공개 | 허용(독립 축). "○○님 외 3명이 응원" + 워드맵 없음 |
| 설정을 나중에 비공개로 전환 | 이미 캐시된 공유 이미지(`wordmap_render_cache`)가 남는다 → 전환 시 **캐시 무효화 + Storage 오브젝트 삭제** 필수. 안 하면 "숨겼는데 URL로 여전히 보인다" |
| 익명 응원자 | 익명은 *응원자가* 고른 것(is_anonymous), 목표 설정과 **AND 결합**. 둘 중 하나라도 숨기면 숨김 |
| 소유자 본인 화면 | 설정과 무관하게 **전부 보인다**(이름·메시지·개별 클로버 개수). 근거: DESIGN.md §6-b′ |

### 3.5 측정 가능한 실패 판정 (pgTAP 회귀 고정 — 회장 지시)
1. **SEC-6a(영구 잠금)**: `supporter_name_visibility`/`message_visibility`를 **어떤 조합으로 설정해도** anon이 `clover_amount`에 도달 가능하면 FAIL. (조합 3×3=9케이스 루프)
2. **SEC-6b**: `cheer_public` 뷰에 `clover_amount`·`supporter_ci` 컬럼이 존재하면 FAIL(`hasnt_column` — 기존 SEC-5d 승계).
3. **SEC-6c**: `message_visibility='PRIVATE'` 목표에 대해 anon `get_wordmap` 반환 행 > 0이면 FAIL.
4. **SEC-6d**: 소유자 본인은 위 3케이스 전부에서 여전히 조회 가능해야 한다(기능 보존 회귀).

| 마이그레이션 시 기존 유저 | 인덱스 DROP만이라 데이터 변경 0. 롤백 = 인덱스 재생성(단, 그 시점 중복이 있으면 실패 — 되돌리기 비대칭임을 인지) |

### 4.7 측정 가능한 실패 판정
1. 한 계정으로 활성 목표 2개 생성 → 실패하면 FAIL.
2. 활성 목표 2개 상태에서 `/home` 렌더 → 2개 다 보이지 않으면 FAIL.
3. 활성 목표 4개째 생성 시도 → 생성되면 FAIL(상한 미작동).
4. 목표 2개 각각에 응원 결제 → `clover_balance` 합계가 두 결제의 합과 다르면 FAIL(원장 정합).

## 5. F-C. 로그인 응원자 경험 (⭐ 최우선)

### 5.1 절대 제약 (먼저 못 박음)
- ⛔ **로그인 강제 금지. 게스트 결제 유지.** 근거: `user-flow.md` §5-4 🔒 확정 + `docs/risks.md` R3(결제 마찰과 전환 위험) + `persona.md` B-1 "결제 마찰 최소, 깨지면 안 씀".
- ⛔ **클로버 적립·응원 리워드·포인트백 절대 금지.** 근거: 응원자에게 잔액을 쥐여주는 순간 우리가 **선불충전금을 보유**하게 되어 `risks.md` #1 옵션 A(자금 무보유 패스스루)가 붕괴한다. `architecture.md` §2.3이 "클로버=충전형 아님"으로 등록 회피를 논증하고 있는데, 응원자 적립은 그 논증의 대전제를 파괴한다. **이 금지는 UX 취향이 아니라 존립 조건이다.**

### 5.2 계정 승격 (결제 완료 화면에서만)
- **입력**: 게스트 세션(`is_anonymous=true`)으로 완료된 결제 + 사용자의 카카오 로그인 동의.
- **출력**: 완료 화면 하단 subtle 카드 — "이 응원, 내 기록으로 남길까요?" → 카카오 로그인 1탭 → 게스트 세션의 응원이 정식 계정에 **귀속**.
- **노출 위치 제한**: 결제 완료 화면 **1곳만**. 목표 페이지·시트·홈에 로그인 유도 배너 추가 금지. 근거: DESIGN.md §5-3(강제 호혜·유도 UI 금지) + §6 "다음 행동 1개".
- ⚠️ **기술 갈림길 → §9-Q6**: 게스트 응원의 계정 귀속을 어떻게 하느냐. (a) Supabase anonymous → 소셜 **링크(linkIdentity)** 로 같은 uid 유지 (b) 새 계정 생성 후 `cheer` 행 소유자 재지정. (a)는 uid 보존으로 데이터 이동이 없지만 카카오가 커스텀 OAuth라 링크 경로 검증이 필요하고, (b)는 결제·원장 참조를 손대는 위험한 변경이다.

### 5.3 마이페이지 "내가 응원한 목표"
- **입력**: `auth.uid()` (정식 계정만. 게스트는 이 화면 없음).
- **출력**: 내가 응원한 목표 리스트 — 목표 제목·상대 닉네임·응원 시각·**내가 보낸 금액(본인만)**·목표 현재 상태(진행중/마감).
- **데이터**: 신규 테이블 불필요. `cheer`에 **응원자 식별 컬럼이 필요**하다 — 현행 `cheer`는 `supporter_ci`(암호화)와 `display_name`뿐이고 **응원자 계정 FK가 없다.**
  ```
  ALTER TABLE cheer ADD COLUMN supporter_member_id uuid NULL REFERENCES member(id);
  ```
  게스트 결제는 NULL 유지(그래서 게스트에겐 이 화면이 없다 = 승격 유인).
- **RLS 신설**: `cheer_select_own_supporter` — `auth.uid() = supporter_member_id`. ⚠️ **이 정책이 금액 잠금(§3.5)을 뚫지 않는지가 최대 위험.** 응원자는 **자기가 보낸 금액만** 봐야 하고, 같은 목표의 **다른 사람 응원 금액은 못 봐야** 한다. 행 단위 정책이므로 `supporter_member_id = auth.uid()` 조건이 이를 보장한다 — 하지만 이건 **pgTAP로 못 박지 않으면 다음 리팩터에서 깨진다**(§5.6-3).

### 5.4 감사 1회 단방향 채널
- **가치**: 받는 사람이 "고마워"를 딱 한 번 보낼 수 있게 하되, **대화가 시작되지 않게** 한다.
- **입력**: 소유자가 특정 `cheer`에 대해 감사 메시지 **최대 200자, 응원 1건당 정확히 1회**.
- **출력**: 응원자의 마이페이지 목록 행에 감사 문구 표시(+ 알림 1회). **응원자는 답장할 수 없다**(입력 UI 자체가 없음).
- **데이터**:
  ```
  ALTER TABLE cheer
    ADD COLUMN thanks_message varchar(200) NULL,
    ADD COLUMN thanks_sent_at timestamptz NULL;
  ```
  1회 제약 = `thanks_sent_at IS NULL`일 때만 UPDATE 허용(RLS/트리거).
- ⚠️ **에토스 충돌 검토**: One Thing은 "감사답장 의무 0"이다. 감사 채널이 **의무처럼 보이면 그 자체가 위반.** 방어 3개: ①미전송 감사에 배지·카운트·독촉 **금지**(안 보내도 화면에 흔적 없음) ②"감사 보내기"는 primary 아님(ghost) ③"N명에게 감사 안 함" 같은 미완료 표시 금지. 근거: `DESIGN.md` §5-3.
- ⚠️ **모더레이션**: 감사 메시지도 사용자 생성 텍스트다 → **신고 대상에 포함**해야 한다(§5.5 선결 조건과 연결). 안 하면 소유자가 응원자에게 욕설을 보낼 수 있는 무감시 채널이 열린다.

### 5.5 경계·예외
| 상태 | 처리 |
|---|---|
| 게스트가 마이페이지 접근 | 라우팅 = "응원 기록은 로그인하면 남아요" + 로그인. dead-end 아님 |
| 승격 전 게스트 응원 | `supporter_member_id` NULL → 승격해도 **과거 응원은 안 보인다**(Q6-(a) 선택 시에만 보임). 이 차이가 Q6의 실질 비용 |
| 응원한 목표가 PRIVATE로 전환됨 | 내 응원 기록은 남되 목표 링크는 비활성 + "지금은 볼 수 없어요" |
| 응원한 목표가 삭제됨 | 기록 유지(제목은 스냅샷 필요할 수 있음 — soft-delete라 조인 가능) |
| 환불된 응원 | 목록에 "환불됨" 표기. 숨기면 CS 분쟁 |
| 감사 메시지에 연락처 유도 | 신고 경로로 처리(§5.5 선결) |

### 5.6 측정 가능한 실패 판정
1. 로그인 없이 결제 완료 → 완료 화면 도달 실패하면 FAIL(게스트 경로 회귀).
2. 결제 완료 화면 **외** 어느 화면에서든 로그인 유도 배너가 노출되면 FAIL.
3. **SEC-7**: 사용자 B가 A의 응원 금액을 조회 가능하면 FAIL(같은 목표 응원자끼리 금액 상호 노출 = 신설 정책의 최대 사고 시나리오).
4. 같은 `cheer`에 감사 2회 전송 성공 시 FAIL.
5. 응원자 화면·API 응답 어디에도 응원자 잔액/적립 필드가 존재하면 FAIL(§5.1 존립 조건).

## 6. F-E. 마이페이지 · F-F. 카테고리 태그

### 6.1 ⛔ 선결 조건 — 인입구보다 읽는 화면이 먼저
현재 신고·문의를 **읽을 관리자 경로가 없다**(`backlog-2026-07-20.md` F3: *"신고 접수 시 오류 + 관리자 확인 경로 없음"*; `user-flow.md` §6-2: admin 화면 = MVP 의도적 제외).

> **규칙: 고객센터 문의 폼(신규 인입구)은 관리자 확인 경로가 서기 전에는 출시하지 않는다.** 근거: 접수만 되고 아무도 안 읽는 창구는 CS 부채가 아니라 **신뢰 파괴**다(사용자는 답을 기다리는데 큐가 존재하지 않음). "개별 답변 드리지 않습니다" 고지는 *답장 의무*를 면제할 뿐 *읽을 의무*를 면제하지 않는다.
> **최소 형태(과투자 방지)**: 풀 admin UI 불필요. `report` + `inquiry` 테이블을 **service_role로 읽는 단일 목록 화면 1개**(또는 검증된 운영자 계정 전용 라우트). 규모 = S.

### 6.2 마이페이지 구성 (6항목)
| 항목 | 내용 | 데이터/API | 상태 |
|---|---|---|---|
| 알림 | 인앱 알림 목록 + 수신 설정(알림톡 on/off) | `notification`(N1) + `member.alimtalk_opt_in boolean` 신설 | 신규 컬럼 1 |
| 프로필 | 카카오 프로필 이미지·닉네임 연동 + 한 줄 소개(선택) | `member.profile_image`(이미 존재) + `member.bio varchar(60)` 신설. **카카오 OAuth scope에 profile_image 포함 여부 확인 필요** | 백로그 F2 해소 |
| 계정 관리 | 로그아웃 · 회원 탈퇴 | 탈퇴 = ⚠️ **클로버 잔액 있으면 탈퇴 차단 또는 선환전 강제**(돈이 남은 계정 삭제 = 분쟁) | 신규 |
| 결제·정산 관리 | **"준비중" 뼈대만** — 토스 상점 심사 대기 | 화면만, API 없음 | 뼈대 |
| 이용약관 | 기존 `/terms`·`/privacy` 링크 | 라우트 존재 | 링크만 |
| 고객센터 | FAQ + **운영자 소통 일방향 폼 1개** | `inquiry` 신설. **§6.1 선결** | 선결 종속 |

- **문의 폼 스펙**: 본문 1,000자 · 카테고리 4종(결제/계정/신고/기타) · **1일 3건 제한**(어뷰징) · 제출 화면에 **"개별 답변은 드리지 않습니다"를 제출 버튼 위에 명시**(제출 후 고지 = 다크패턴).
  ```
  CREATE TABLE inquiry (id bigint GENERATED ALWAYS AS IDENTITY PK,
    member_id uuid NULL REFERENCES member(id), category text NOT NULL,
    body varchar(1000) NOT NULL, status text NOT NULL DEFAULT 'OPEN',
    created_at timestamptz NOT NULL DEFAULT now());
  ```
  RLS: insert = 본인/게스트 허용, select = **service_role만**(본인 조회조차 v2 미제공 — 답변이 없으므로 볼 것이 없다).

## 10.1 §10-1 — 소셜 로그인 버튼은 앱 출시까지 보류

- **현재 결정**: `SHOW_SOCIAL_LOGIN=false`를 유지해 구글·애플 등 소셜 버튼을 앱 출시 시점까지 노출하지 않는다. 카카오 인증 및 전화번호 수집 경로는 환전·알림 운영을 위해 보존한다. 구글 코드는 삭제하지 않지만 **현재 활성 기능으로 보고하지 않는다**.
- **입력/출력**:
  - 입력 = LoginSheet의 provider 버튼. 구글 코드는 배선돼 있지만 현재 `SHOW_SOCIAL_LOGIN=false`(line 80)라 사용자에게 노출되지 않는다. provider 콘솔 설정과 운영 E2E 없이 플래그만 바꾸지 않는다.
  - 출력 = 현재 화면에는 보류 중인 소셜 버튼이 나타나지 않는다. 앱 출시 전 별도 승인과 provider 실검증을 거쳐 플래그를 전환한다.
- **근거**: FDD F8이 로그인을 *"카카오 primary(+구글/애플)"*로 이미 명시(`fdd-haenael-ge-v0.1.0.md:75`). 애플은 Supabase 프로젝트 + Apple Developer(Services ID·Team ID·Key) **별도 설정 의존**(`LoginSheet.tsx:365` 주석)이라 콘솔 비용 대비 초기 가치 낮음. **네이버는 신규 요청이나 알림톡 도달에 무기여**(§10.2 — 알림톡은 카카오 종속이라 네이버 번호로 카카오 알림톡을 못 보냄)라 후순위.
- **재개 조건**: 앱 출시 직전 Supabase Google provider 활성, OAuth 동의화면·redirect URI 확인, 운영 로그인 E2E 통과가 모두 확보됐을 때만 `SHOW_SOCIAL_LOGIN=true`를 검토한다. 플래그 1줄만 바꾸고 완료로 간주하면 안 된다.

## 10.2 §10-2 — 알림톡 도달 = 전화번호 확보 (⚠️ 로그인 확대와 별개 축)

- **결정**: 카카오 알림톡 도달을 위해 **①카카오 앱을 비즈앱으로 전환 → ②`phone_number` 동의항목(scope) 추가 → ③카카오 로그인 시 사용자 전화번호 자동 수신 → ④`member.phone` 컬럼에 저장 → ⑤`notify` EF의 ALIMTALK 경로 활성.**
- **⚠️ 반드시 명시하는 설계 비대칭 (핵심)**: **알림톡은 카카오 생태계 종속이다.** 전화번호는 **카카오 로그인 동의로만** 들어온다. 따라서:
  - **카카오로 로그인한 유저** → `member.phone` 있음 → **ALIMTALK 도달** ✅
  - **구글로 로그인한 유저** → 전화번호 없음(구글 OAuth는 전화번호 scope를 표준 제공하지 않음) → **INAPP 폴백만** ⚠️
  - → **"로그인 provider 확대(§10-1)"와 "알림 도달(§10-2)"은 다른 축이다.** 구글 유저를 아무리 늘려도 그들의 알림톡 도달률은 0이다. 이 문장을 문서에 못박는 이유 = 다음에 "구글 로그인 늘렸으니 알림도 잘 가겠지"라는 오추론을 차단하기 위해서다.
- **입력/출력 (데이터 흐름)**:
  - 입력 = 카카오 로그인 콜백에서 받은 `kakao_account.phone_number`(비즈앱 + `phone_number` scope 동의 시에만 payload에 포함).
  - 처리 = `auth-kakao` EF가 세션 확립 시 `member.phone`에 저장한다. 환전 신청과 지급 완료 시 해당 번호가 있으면 `notify` EF의 ALIMTALK 경로를 호출하고, 없으면 INAPP 폴백을 유지한다.
  - 출력 = `notify` EF는 `phone` 파라미터가 있으면 ALIMTALK, 없으면 INAPP으로 처리한다. `member.phone` 컬럼과 환전 알림 2종은 운영 반영됐으며 더 이상 미구현 blocker가 아니다.
- **운영 반영 데이터 항목**:
  ```
  ALTER TABLE member ADD COLUMN phone varchar(20) NULL;  -- 카카오 phone_number scope로만 채워짐, 구글 유저는 NULL
  ```
- **운영 근거**: `20260805010000_member_phone_alimtalk.sql`에 `member.phone`이 존재한다. 운영에서 `CASHOUT_REQUESTED`와 `CASHOUT_PAID` 알림톡 각 1건이 발송됐고 템플릿 2종 등록도 확인됐다. phone이 없으면 INAPP 폴백하는 계약은 유지한다.
- **⚠️ 알림톡 부가 의존성(FDD F9 승계)**: 비즈채널 개설 + **템플릿 사전심사**(목표 제목 변수 슬롯 = §4.3-6과 동일 재심사) + 건당 발송비 + **정보성만(마케팅 금지)**. 이 심사 리드타임 때문에 §7.2 순서 4번을 병렬 조기 신청으로 둔다.

## 10.3 §10-3 — 환전 신청 신원 정책 = 확인된 미성년만 차단

- **운영 결정:** PASS 완료 또는 KYC 기록 존재는 환전 **신청 선행조건이 아니다**. 가입 직후처럼 KYC 기록이 없는 회원도 신청할 수 있다. 최신 KYC 결과가 `is_adult=false`로 확인된 회원만 신청을 차단한다.
- **지급 단계 수집:** 주민등록번호와 실제 지급에 필요한 신원·세무 정보는 운영자가 지급을 실행하는 단계에서 수집한다. 신청 화면이나 로그인·알림에서 주민등록번호를 요구하지 않는다.
- **알림과 신원의 분리:** 알림톡에 필요한 값은 카카오 `phone_number` 동의로 얻는 연락처다. 전화번호 확보와 PASS 실명 확인을 같은 게이트로 묶지 않는다.
- **근거:** 회장 결정이 반영된 `20260825010000_cashout_verified_minor_only.sql`은 "가입 직후 계정은 통과하고 확인된 미성년만 차단"을 명시한다. `docs/user-flow.md` §1의 엣지 상태와 `docs/fdd-haenael-ge-cashout-clover-lock-v1.1.0.md` R2도 같은 계약을 따른다.
- **법률·세무 경계:** 이 운영 계약은 법률 또는 세무 검토 완료를 뜻하지 않는다. 미성년 지급, 법정대리인 동의, 주민등록번호 수집·보관·파기, 원천징수 주체와 지급명세 의무는 `docs/risks.md` R2·R6의 미해소 위험으로 유지한다.

## 10.4 §10 용어 고정 (원칙 1)

| 용어 | 정의 | 값/범위 |
|---|---|---|
| **provider (로그인)** | 사용자의 신원을 확인해 세션을 주는 외부 제공자 | 현재 소셜 버튼 비노출. 카카오 인증 경로 운영. 구글·애플·네이버는 앱 출시까지 보류 |
| **채널 (알림)** | 알림을 전달하는 수단 | `ALIMTALK`(카카오, phone 필요) / `INAPP`(폴백, phone 불필요) |
| **phone (전화번호)** | 알림톡 발송에만 쓰는 연락처. **카카오 phone_number scope로만** 유입 | `member.phone varchar(20) NULL` |
| **본인인증 (PASS) / KYC 기록** | 최신 기록이 있으면 미성년 여부를 판정하는 근거. **기록 없음은 신청 차단 사유가 아님** | `kyc_verification`; 최신 `is_adult=false`만 신청 차단 |
| **지급 신원정보** | 실제 지급과 세무 처리에 필요한 정보. 주민등록번호는 이 단계에서만 수집 | 운영 지급 단계. 수집·보관·파기는 법률·세무 검토 필요 |

> ⚠️ **phone ≠ 본인인증 ≠ 지급 신원정보.** phone은 알림 연락처다. KYC 기록은 확인된 미성년 차단 근거다. 주민등록번호는 실제 지급 단계의 별도 민감정보다. 셋을 한 번에 수집하지 않는다.

> 아래 Q9~Q11은 의사결정 당시의 맥락 보존용이다. 현재 결정은 바로 위 §10.7 표가 정본이며, 아래 추천과 회수 문구를 다시 실행하지 않는다.

**⛔ Q9. 구글 provider를 Supabase 콘솔에서 활성화할까?**
- 무엇을: `SHOW_SOCIAL_LOGIN=true`로 되돌리기 전에 **Supabase 대시보드 → Authentication → Providers → Google 활성 + OAuth Client ID/Secret 입력**(Google Cloud Console에서 OAuth 동의화면·자격증명 발급)이 선행돼야 한다.
- 하면: 구글 로그인 즉시 동작(코드 이미 존재). 안 하면: 버튼 눌러도 `signInWithOAuth` 에러 → 친절 메시지 폴백(`describeOAuthError`, 이미 방어됨).
- 추천: **활성화.** 근거: 코드·테스트가 이미 완성돼 있어 콘솔 설정만으로 provider 1개가 늘어남(한계비용 최소). **이 작업은 회장 계정 콘솔 조작이라 세션이 못 함 → 회장 캡처 확인 필요**(postagi-app-deploy 원칙).

**⛔ Q10. 카카오 비즈앱 전환 + `phone_number` 동의항목 신청을 진행할까?** (과거 질문, 현재 해소)
- 무엇을: **카카오 디벨로퍼스 → 앱 → 비즈앱 전환**(사업자등록번호 또는 개인개발자 경로) → **동의항목에서 `phone_number`(전화번호) 사용 신청**. 검색 확인 결과 **`phone_number` scope는 비즈앱 전환 + 사업자등록 정보가 사실상 전제**다([카카오 데브톡](https://devtalk.kakao.com/t/id-1496529/150398) — "카카오계정(전화번호) 수집 권한은 비즈앱 전환 후 사업자 정보로 신청").
- 하면: 카카오 유저 전화번호 자동 수신 → ALIMTALK 도달. 안 하면: **알림톡 영구 비활성**(모든 유저 INAPP만). §10.2 전체가 콘솔 승인에 종속.
- ⚠️ **`⛔ 회수 필요: 카카오 비즈앱 전환에 사업자등록번호가 필요한지 / 개인개발자 경로로 phone_number scope가 승인되는지를 회장이 카카오 디벨로퍼스 콘솔에서 확인해야 한다.`** 사업자등록이 필수라면 알림톡 도달은 사업자 등록 완료 이후로 밀린다(일정 의존성). 개인개발자 경로 가능 여부는 카카오 심사 재량이라 세션이 단정 불가.
- 추천: **비즈앱 전환은 진행하되, 사업자등록 의존성을 회장이 먼저 콘솔에서 확인.** 근거: 알림 도달은 `docs/risks.md` R10의 재방문 트리거이나 카카오 심사 리드타임이 있어 조기 착수 이득.

**⛔ Q11. 알림톡 템플릿을 어떤 문구로 사전심사 신청할까?**
- 무엇을: 목표 제목 변수를 포함한 정보성 템플릿(예: *"'{목표제목}'에 조용한 응원이 도착했어요"*). §4.3-6과 동일 변수 슬롯.
- 하면: 심사 통과 시 다중 목표에서도 목표 특정 알림 가능. 안 하면: 변수 없는 범용 문구로 다중 목표에서 "어느 목표인지" 모호.
- 추천: **변수 포함 템플릿으로 조기 신청**(심사 리드타임 흡수). 근거: FDD F9 + §4.3-6. 금액 변수는 **절대 미포함**(3층 정책, `20260720010000:24`).

## 10.8 §10 측정 가능한 실패 판정

1. 앱 출시 범위에서 구글 로그인을 재개할 경우 `SHOW_SOCIAL_LOGIN=true` + Supabase Google provider 활성 후 구글 버튼 클릭 → 세션 확립 실패하면 FAIL(구글 경로 회귀). 현재 릴리스의 버튼 비노출은 PASS 조건이다.
2. 카카오 phone scope 동의 후 로그인 → `member.phone`이 NULL이면 FAIL(수신 파이프 미배선).
3. `member.phone` 있는 소유자에게 응원 도착 → `notification.channel != 'ALIMTALK'`이면 FAIL(ALIMTALK 미활성).
4. `member.phone` NULL(구글 유저) 소유자에게 응원 도착 → `channel != 'INAPP'`이면 FAIL(폴백 회귀).
5. 로그인·알림 또는 환전 **신청** 단계에서 PASS 완료나 주민등록번호를 선행 요구하면 FAIL(§10.3).
6. 최신 KYC 기록이 없다는 이유만으로 환전 신청을 거부하면 FAIL. 최신 결과가 `is_adult=false`인데 신청을 허용해도 FAIL.
7. 알림·로그인 payload 어디에도 응원 **금액**이 실리면 FAIL(3층 정책).

## 10.9 운영 환전 임계 계약 (2026-08-29 보정)

### 요구 CASHOUT-THRESHOLD-01

- **목적:** 시스템 지급 클로버가 섞여 있어도 최소 환전 도달 여부와 실제 지급 가능액을 서로 다른 값으로 판정한다.
- **입력:** `total_clover`, `payable_clover`, `requested_clover`, 최소 기준 `30`.
- **출력:** 도달 여부는 `total_clover >= 30`, 신청 허용은 `1 <= requested_clover <= payable_clover`로 판정한다.
- **불변식:** 시스템 지급 클로버는 최소 기준 도달에는 포함할 수 있지만 실제 지급액에는 포함하지 않는다.

```gherkin
Scenario: 총 보유 30클로버 중 지급가능 27클로버를 신청한다
  Given 로그인 회원의 총 보유가 30클로버이고 지급가능액이 27클로버다
  When 회원이 27클로버 환전을 신청한다
  Then 최소 기준 도달 판정은 통과한다
  And 신청액은 지급가능 상한 이내이므로 REQUESTED 상태가 생성된다

Scenario: 지급가능액을 초과해 신청한다
  Given 로그인 회원의 총 보유가 30클로버이고 지급가능액이 27클로버다
  When 회원이 28클로버 환전을 신청한다
  Then 신청은 거부되고 환전 원장과 잔액은 바뀌지 않는다
```

### 검증 상태

- 로컬 PostgREST에서 총 30, 지급가능 27, 신청 27이 HTTP 200과 `REQUESTED`를 반환했다.
- 운영 migration history와 함수 실덤프에서 `v_total < v_min`과 `p_clover_amount > v_payable` 분리 판정을 확인했다.
- 운영에 동일 상태의 실제 대상 계정이 현재 0개이므로 자연 발생 실사용 신청은 **미검증**이다. 시험 거래를 만들어 이 경계를 억지로 닫지 않는다.

## 11. kill-criteria (기간·모집단·수치 고정) *(v0.3.0 §10 → 재번호)*

### 11.1 제품 전체 3대 종료 기준

1. **리텐션 사망:** 공개 유입을 시작한 뒤 **8주**, 그 기간 신규로 목표를 만들고 응원 링크를 1회 이상 공유한 소유자 **30명 이상**을 모집단으로 잡는다. 이들의 **W4 목표 기록 재방문율이 20% 미만**이면 기록·공유 루프를 중단하고 별도 habit tracker 기능을 더 만들지 않는다.
2. **결제 전환 사망:** 유료 결제를 재개한 뒤 **4주**, 결제 시작 이벤트를 발생시킨 고유 응원자 **50명 이상**에서 `payment_success / cheer_started`가 **40% 미만**이거나, 첫 결제 성공자 중 4주 안에 두 번째 응원을 한 비율이 **10% 미만**이면 즉시 적립형 금전 응원 One Thing을 피벗 후보로 올린다.
3. **단위경제 사망:** 유료 결제 재개 후 **8주 또는 성공 결제 30건 도달 시점 중 늦은 때**, 해당 결제 전건을 모집단으로 PG비·환불·알림·CS 직접비를 포함한 건당 공헌이익을 계산한다. 평균 공헌이익이 **0원 이하**이거나 관찰 LTV/CAC가 **1.0 미만**이면 유료 유입을 중단하고 가격·최소 결제액·정산 구조를 재설계한다.

> 모집단 최소치에 못 미치면 성공으로 간주하지 않는다. 그 경우 판정은 **데이터 부족**이며, 유료 확장도 보류한다.

### 11.2 v2 기능별 축소 기준

아래는 제품 전체를 죽이는 기준이 아니라 해당 기능을 축소하거나 되돌리는 기준이다.

1. **다중 목표 무효 판정**: 다중 목표 출시 **6주 내**, 목표를 2개 이상 만든 계정 비율이 **전체 활성 소유자의 10% 미만**이면 → 다중은 회장 개인 니즈였고 일반 사용자 니즈가 아니다. 홈 리스트 UI를 단순화(1목표 + "다른 목표" 접기)로 되돌린다.
2. **응원자 계정 무효 판정**: 계정 승격 CTA 노출 대비 승격률이 **4주 내 5% 미만**이면 → 응원자는 기록을 원하지 않는다. 감사 채널(§5.4)까지 함께 동결하고 게스트 전용으로 회귀한다.
3. **프라이버시 설정 무효 판정**: 출시 **8주 내** 기본값이 아닌 값으로 바꾼 목표가 **3% 미만**이면 → 설정 UI를 마이페이지 깊은 곳으로 내려 온보딩 마찰을 제거한다(기능 제거는 하지 않음 — 보안 경계는 남긴다).
4. **문의 폼 즉시 롤백**: 출시 후 **1주 내** 미확인 문의가 **50건**을 넘거나 응답 필요 문의(환불·오작동)가 **10건**을 넘으면 폼을 내리고 이메일 안내로 대체한다.
5. **ⓥ 알림톡 도달 무효 판정 (v0.4.0)**: 카카오 비즈앱 승인 + phone scope 활성 후 **4주 내**, 카카오 로그인 소유자 중 `member.phone` 확보율이 **40% 미만**이거나 ALIMTALK 발송 성공률이 **70% 미만**이면 → 알림톡 투자(비즈앱·건당비·템플릿 심사) 대비 도달이 안 나오는 것이다. INAPP 알림 강화(재방문 시 배지·요약)로 무게중심을 옮기고 알림톡은 opt-in 유저 한정으로 축소한다.

## 12. 셀프심문 (CoVe) — "이 기획이 틀렸다면 어디서 틀렸나" *(v0.3.0 §11 → 재번호, v0.4.0 항목 추가)*

**Q1. 다중 목표가 실제로는 회장 1인의 테스트 니즈이고, 실사용자는 목표 1개면 충분한 것 아닌가?**
자답: **가능성 있다.** 근거 표본이 회장 발화 1건 + 페르소나 문서의 한서연(가공된 인물)뿐이다. 실사용자 데이터는 0이다(결제 미오픈). 다만 되돌림 비용이 비대칭이다 — 제약 해제는 인덱스 DROP 1줄이고, UI는 "목표 1개면 지금 화면과 동일하게 보이는" 리스트로 만들면 나쁜 경우에도 손실이 작다. → **반영**: §11-1에 6주/10% kill 기준을 넣고, 홈 리스트를 "1개일 때 현행과 시각적으로 동일"하게 설계할 것을 §4.3-1의 암묵 요건으로 못 박았다.

**Q2. 응원자 마이페이지가 "조용함"을 깨는 것 아닌가 — 응원자가 자기 응원을 관리하기 시작하면 응원이 거래가 된다.**
자답: 부분적으로 맞다. 그러나 `persona.md` B-1 민지의 실제 페인은 "생색내고 싶다"가 아니라 **"내가 응원한 게 닿았는지 모르겠다"**(§B-1 Emotional: "그 애가 알게는 하고 싶다")이다. 마이페이지는 생색 도구가 아니라 **불확실성 해소** 도구다. → **반영**: 응원자 화면에 합계·순위·스트릭·레벨 표시 금지(DESIGN.md §5-2 확장 적용).

**Q3. 이 기획의 가장 위험한 단일 지점은?**
자답: **§5.3의 신설 RLS 정책**이다. 지금까지 `cheer` 접근은 "소유자만"이라는 단일 축이었는데, 여기에 "응원자 본인"이라는 **두 번째 접근 축**이 생긴다. 축이 둘이 되는 순간 조합 실수(예: 정책 OR 결합으로 같은 목표의 다른 응원 노출)가 High 유출이 된다 — `20260719000000` 마이그레이션이 고친 사고와 **정확히 같은 유형**이다. → **반영**: §5.6-3에 SEC-7을 별도 판정으로 세우고, §7.2 순서에서 5번 항목에 pgTAP를 붙여 놓았다. 추가로 **구현 시 Codex 크로스리뷰 대상**임을 지정한다.

**ⓥ Q4 (v0.4.0). 소셜 로그인 보류가 신규 유입을 과도하게 제한하지 않나? (red-team)**
자답: 틀릴 가능성은 카카오 연결을 꺼리는 신규 사용자가 로그인 전에 이탈하는 경우다. 그러나 구글·애플 버튼은 운영 provider E2E가 끝나지 않아 지금 노출하면 선택지는 늘어도 성공 경로는 늘지 않는다. 현재는 카카오 한 경로의 성공률과 `member.phone` 확보율을 계측하고, 앱 출시 범위가 확정될 때 운영 OAuth E2E를 통과한 provider만 순차 재개한다. 따라서 보류는 영구 배제가 아니라 검증되지 않은 진입로를 숨기는 릴리스 안전 결정이다.

**Q5. 0번 게이트 — 매칭 스킬을 실제로 호출했나?**
자답: 호출하지 않았고, 그 사유를 푸터에 선언했다. `document-generate`는 기존 코드로부터 문서를 역생성하는 도구인데, 본 산출물은 **기존 승인 PRD(v0.3.0)를 계승한 forward 델타 개정**이라 역생성 대상이 아니다. `spec`은 대화형이라 서브에이전트 스코프 밖. 벤치마크는 WebSearch 1건(카카오 phone scope 비즈앱 의존) 실행.

## 13. 레드팀 (회의적 투자자 관점) *(v0.3.0 §12 → 재번호)*

**공격**: "결제도 못 여는 서비스가(백로그 F1: 토스 심사 대기) 프라이버시 설정 3값 enum과 마이페이지 6개 항목을 만들고 있다. 이건 제품 개발이 아니라 **출시 회피**다. 검증되지 않은 코어(친구가 실제로 돈을 내는가)를 두고 주변부를 정교하게 다듬는 건 전형적인 pre-PMF 낭비다."

**방어와 수정**: 이 공격은 **절반 유효하다.** 실제로 v2에서 콜드스타트 전환에 직접 기여하는 항목은 **0개**다 — 전부 소유자·응원자의 *사후* 경험이다. 다만 ①결제 오픈은 외부 심사(회장 트랙)라 개발이 기다리는 시간이 존재하고 ②F-B(금액 잠금)는 이미 High 유출을 한 번 겪은 영역의 **회귀 방어**이며 ③§6.1(신고·문의 읽기)은 미출시 상태에서도 법적·신뢰 최소선이다.

→ **수정 반영**: §7.2 구현 순서를 **"보안·선결(0~2) → 무거운 UI(3) → 나머지"** 로 재배열해, 결제가 열리면 언제든 3 이후를 중단하고 콜드스타트 계측으로 전환할 수 있게 했다. **v2는 언제든 항목 5~9에서 멈출 수 있는 순서로 설계돼 있다.**

**ⓥ v0.4.0 추가 공격**: "소셜 로그인을 보류하면 유입을 스스로 줄이는 것 아닌가?" → **방어**: 운영 검증이 끝나지 않은 버튼은 선택지가 아니라 실패 경로다. 카카오 로그인과 전화번호·알림톡은 운영에서 관찰됐고, 구글·애플은 앱 출시 때 provider 설정과 운영 OAuth E2E를 통과한 뒤 재개한다. 현재의 보류는 기능 폐기가 아니라 검증 순서의 통제다.
