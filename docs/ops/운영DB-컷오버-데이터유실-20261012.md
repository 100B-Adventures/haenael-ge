# P0. 운영 DB 컷오버로 기존 데이터가 끊겼다 (2026-10-12)

회장 질문: "데이터가 없어진거냐? 말이 안되잖아? 지금 Db 옮긴적있나?
예전에 정산 결제 회원가입 데이터 다 기록되어있는데 어디가있어"

## 결론

**데이터는 지워지지 않았다. 살아 있다. 다만 운영이 다른 데이터베이스를 보고 있다.**

2026-10-07 에 새 Supabase 프로젝트를 만들고 2026-10-09 에 운영을 그쪽으로 옮겼는데,
**기존 데이터를 옮기지 않았다.** 그래서 새 프로젝트는 스키마만 있고 내용이 비어 있다.

| | 이전 운영 DB | 현재 운영 DB |
|---|---|---|
| 프로젝트 | `gmpwrcxpvgylmllasoqy` | `ossvejipdivgxzcqszbw` |
| 생성 | (2026-07 이전) | 2026-10-07 08:52 |
| 상태 | **살아 있음, 응답함** | 살아 있음 |
| 목표 | **2건** | **0건** |
| 응원(결제) | **24건** | **0건** |

이전 DB 의 실제 목표 두 건:

- `7vb3j7t` 공인중개사 2차 합격🖤 해낼게 (2026-07-30)
- `knirdtaq` 해낼게를 해낼게 (2026-07-20)

회장이 누른 공유 링크는 이 둘 중 하나다. 현재 운영은 새 DB 를 보므로 404 가 난다.

## 어떻게 찾았나

레포와 로컬에는 이전 프로젝트 주소가 어디에도 없었다(`wiki/ops/인프라.md` 도
"이전 운영 DB: 레포에 박혀 있지 않음" 이라고만 적고 있었다).
**컷오버 이전 Vercel 배포본의 자바스크립트 번들에 이전 주소와 공개 키가 그대로 박혀
있어서** 그것을 꺼내 조회했다. 16일·21일·73일 전 배포본 세 개가 모두 같은 주소를 가리킨다.

## 회장이 정해야 할 것

**무엇을.** 이전 DB 의 데이터를 현재 DB 로 옮길지, 아니면 운영을 이전 DB 로 되돌릴지.

**옮기면.** 새 프로젝트의 최신 스키마(마이그레이션 44개)를 그대로 쓴다. 다만 두 DB 의
스키마가 그사이 갈라졌으면 변환이 필요하고, `auth.users` 를 옮겨야 기존 회원이
그대로 로그인된다. 결제·정산 원장은 금액이 걸린 데이터라 검증이 필요하다.

**되돌리면.** 지금 당장 데이터가 보인다. 대신 10-07 이후 새 프로젝트에만 적용한
마이그레이션과 엣지함수 배포를 이전 DB 에 다시 맞춰야 한다.

**추천: 옮긴다.** 되돌리기는 새 프로젝트에서 한 작업(마이그레이션 44개, 엣지함수 11개,
함수 시크릿 13개)을 버리게 된다. 데이터는 2건·24건으로 작아서 옮기는 쪽이 싸다.

**옮기려면 두 프로젝트의 서버 키가 필요하고, 그건 회장 계정에만 있다.**
현재 로컬 `haenael-ge.env` 의 service_role 키는 **이미 무효**다(`Invalid API key`).

## 곁다리

- 현재 운영 DB 는 레거시 JWT 키를 폐기하고 새 형식(`sb_publishable_`)으로 넘어갔다.
  로컬에 저장된 service_role 키가 그래서 안 먹는다. 새 형식 서버 키를 받아 보관해야 한다.
- 이전 DB 는 아직 레거시 키로 열린다. 데이터를 옮기기 전까지 **삭제하면 안 된다.**
