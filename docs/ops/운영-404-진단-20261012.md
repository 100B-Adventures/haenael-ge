# 운영 `/g/{slug}` "링크를 찾을 수 없어요" 진단 (2026-10-12)

회장 지적: "지금 haenael-ge.vercel.app 들어가면 링크를 찾을 수 없어요 뜨는데 왜 이러냐?
이전 데이터들 다 supabase 적용되어있는거지?"

## 결론

**운영 데이터베이스에 목표가 한 건도 없다.** 코드 결함도, 배포 사고도 아니다.
그 문구는 `web/src/app/g/[slug]/not-found.tsx:23` 에만 있고, 공유 링크 페이지가
해당 slug 를 못 찾았을 때만 나온다.

## 실측

| 확인 | 결과 |
|---|---|
| 루트 `https://haenael-ge.vercel.app/` | HTTP 200, 랜딩 정상 렌더 |
| 404 문구 위치 | `/g/{slug}` 전용 (`not-found.tsx:23`) |
| 운영이 바라보는 Supabase | `ossvejipdivgxzcqszbw` (번들에서 직접 확인) |
| 그 환경변수 생성 시점 | 85일 전, 이후 변경 없음 = **프로젝트를 바꾼 적 없다** |
| `goal_public` 조회(비로그인) | HTTP 200, `[]`, `content-range: */0` = **0건** |
| `goal` 테이블 비로그인 조회 | HTTP 200 `[]` (RLS 로 가려짐, 권한은 아직 있음) |
| `cheer` 테이블 비로그인 조회 | HTTP 401 `42501` (설계대로 권한 회수됨) |

## 0건이 "RLS 에 가려진 것"이 아니라 "진짜 없음"인 근거

`goal_public` 뷰 본문은 `cheer` 를 하위질의로 읽는다. 뷰가 호출자 권한
(`security_invoker`)으로 돌았다면 비로그인 호출에서 **`cheer` 권한 오류(42501)가
떴어야 한다.** 포스트그레스는 결과 행 수와 무관하게 질의에 등장하는 모든 릴레이션의
권한을 실행 시작 시점에 검사하기 때문이다. 실제 응답은 오류 없는 200 이었다.
즉 뷰는 정의자 권한으로 돌았고 **RLS 를 우회해서 읽었는데도 0건**이다.

→ 운영 `goal` 테이블에 공개 가능한 목표가 하나도 없다.

## 왜 비었나 (추정, 미검증)

카카오 가입이 `client_id` placeholder 버그로 막혀 있었고 그 수정이 `9c2a5a6` 이다.
가입이 안 됐으니 운영에서 목표가 만들어진 적이 없을 수 있다. 회장이 가진 링크는
로컬 개발 환경(`127.0.0.1:54321`)에서 만든 것이거나, 해당 목표가 soft-delete
(`deleted_at`) 된 것이다. **둘 중 어느 쪽인지는 서비스 롤 접근 없이는 못 가른다.**

## 가려야 할 것

이 세션의 Supabase CLI 로는 이 프로젝트가 안 보인다(다른 조직 계정).
운영 DB 를 직접 읽어야 다음이 갈린다.

```sql
select count(*) from goal;                       -- 0이면 "만들어진 적 없음"
select count(*) from goal where deleted_at is not null;  -- >0이면 "지워진 것"
select count(*) from auth.users;                 -- 가입 자체가 있었는지
```

## 곁다리로 발견한 것

`20260719000000_cheer_amount_privacy.sql` 이 비로그인 역할의 base 테이블 직접 조회
권한을 회수했는데, `cheer` 는 회수됐고 **`goal` 은 아직 남아 있다**(200 응답).
RLS 가 막고 있어 현재 유출은 없지만 의도와 실물이 어긋난 상태다. 별건으로 정리한다.
