# 해낼게 QA 복구 요청 원문

## 요청 번호

| 요청번호 | 요청 요지 |
|---|---|
| QA-RECOVERY-01 | 기능별 필수 환경변수를 코드에서 도출하고 대상 배포 환경의 실제 존재 여부를 값 노출 없이 검사하며, 누락 시 배포를 막는다. |
| QA-RECOVERY-02 | 최소 환전 기준·잔액 판정·금액 계산의 DB 함수와 화면 기준을 대조해 층간 불일치를 잡는다. |

| QA-RECOVERY-06 | (a)·(b)·(c)를 일부러 깨뜨려 신설 검사가 실제로 실패하는지 증명하고 커밋하지 않는다. |

## Verbatim

> 해낼게(haenael-ge) QA 복구 3종. 2026-08-25 사고에서 QA 가 심각한 결함 3건을 하나도 못 잡았다. 그 계층을 메우는 검사를 신설하라.
>
> ■ 사고 사실(컨트롤러 실측)
> 로컬 단위테스트 263개·브라우저 E2E 12개·시나리오 7종이 전부 GREEN 인데 운영 첫 환전 신청이 실패했다. 못 잡은 결함 3종:
> (a) SUPABASE_SERVICE_ROLE_KEY 가 Vercel 운영 환경에 미등록 → 서버가 DB 에 붙지도 못함
> (b) 최소 환전 기준을 DB 는 총 보유로, 화면은 환전가능액으로 재는 층간 불일치 → 총 30개(개인27+웰컴3) 인데 신청 불가
> (c) 환전 알림톡이 403 으로 죽는데 실패가 삼켜져 0건인지 실패인지 구분 불가
>
> 근본: 시험 데이터를 관문 통과 상태로 심어놓고 로컬에서만 돌렸다. 실사용자 경로와 운영 환경 계층을 한 번도 안 태웠다.
>
> ■ 과제 3개
> 1) 운영 환경변수 존재 점검: 각 기능이 필요로 하는 환경변수 목록을 코드에서 도출하고, 배포 전에 그것들이 대상 환경에 실제로 있는지 확인하는 검사를 만들어라. 값은 절대 출력하지 마라(존재 여부와 이름만). 없으면 배포를 막을 수 있는 형태로.
> 2) 층간 판정기준 대조: DB 함수와 화면이 같은 항목을 같은 기준으로 재는지 확인하는 검사. 최소 환전 기준·잔액 판정·금액 계산이 대상. 이번 (b) 같은 불일치를 잡아야 한다.
> 3) 시험 데이터 기준 교정: supabase/tests/cashout_manual.test.sql 등에서 계정을 관문 통과 상태로 미리 심는 방식을 버리고, 실제 가입 직후 상태에서 시작하도록 바꿔라. 그리고 create_cashout_request 가 RAISE 하는 실패 조건 전체를 목록화해 각각 태우는 케이스를 만들되, 운영 DB 에는 절대 쓰지 마라(로컬/테스트 전용).
>
> ■ 절대 약화 금지
> 계좌 마스킹 검증(web/e2e/cashout-manual.spec.ts, supabase/tests/cashout_security_hardening.test.sql)과 수수료 계산식 검증은 어떤 이유로도 삭제·완화하지 마라.
>
> ■ 완료 조건
> 신설한 검사를 실제로 돌려 결과를 보이고, 위 (a)(b)(c) 각각을 이 검사들이 잡을 수 있음을 증명하라(일부러 깨뜨려서 검사가 실패하는지 확인). 커밋하지 말고 파일:줄로 보고하라.
