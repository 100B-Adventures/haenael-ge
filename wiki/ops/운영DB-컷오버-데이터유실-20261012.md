# P0. 운영 DB 컷오버로 기존 데이터가 끊겼다 (2026-10-12)

회장 질문: "데이터가 없어진거냐? 말이 안되잖아? 지금 Db 옮긴적있나?
예전에 정산 결제 회원가입 데이터 다 기록되어있는데 어디가있어"

## 결론

**데이터는 지워지지 않았다. 살아 있다. 다만 운영이 다른 데이터베이스를 보고 있다.**

2026-10-07 에 새 Supabase 프로젝트를 생성하고 2026-10-09 에 운영 환경변수를 그 프로젝트로 전환했는데,
**스키마 마이그레이션만 적용하고 레코드를 이관하지 않았다.** 그래서 새 프로젝트는 테이블은 있으나 전 테이블 0행이다.

| | 이전 운영 DB | 현재 운영 DB |
|---|---|---|
| 프로젝트 | `gmpwrcxpvgylmllasoqy` | `ossvejipdivgxzcqszbw` |
| 생성 | (2026-07 이전) | 2026-10-07 08:52 |
| 상태 | **살아 있음, 응답함** | 살아 있음 |
| 목표 | **2건** | **0건** |
| 응원(결제) | **24건** | **0건** |

이전 DB 의 실제 목표 두 건:

- `7vb3j7t` 공인중개사 2차 합격🖤 해낼게 (2026-07-30)
- `knirdtaq` 해낼게를 해낼게 (2026-07-20)

회장이 누른 공유 링크는 이 둘 중 하나다. 현재 운영은 새 DB 를 보므로 404 가 난다.

## 어떻게 찾았나

레포와 로컬에는 이전 프로젝트 주소가 어디에도 없었다(`wiki/ops/인프라.md` 도
"이전 운영 DB: 레포에 박혀 있지 않음" 이라고만 적고 있었다).
**컷오버 이전 Vercel 배포본의 자바스크립트 번들에 이전 주소와 공개 키가 그대로 박혀
있어서** 그것을 꺼내 조회했다. 16일·21일·73일 전 배포본 세 개가 모두 같은 주소를 가리킨다.

## 언제 갈렸나 (배포본 추적, 2026-10-12 실측)

회장 질문: "ossvejipdivgxzcqszbw 이거 계속 쓰던거아니야? 뭐가달라진거야"

**계속 쓰던 것이 아니다.** 운영 배포본을 시간순으로 훑어 각 배포가 어느 DB 를 가리키는지 꺼냈다.

| 배포 | 생성 시각 | 가리키는 DB |
|---|---|---|
| haenael-o7o8ukkhr | 2026-09-26 00:16 | **gmpwrcxpvgylmllasoqy (이전)** |
| haenael-i7zo39hpr | **2026-10-09 13:49** | **ossvejipdivgxzcqszbw (현재)** |
| haenael-oir1x2wyb | 2026-10-09 이후 | ossvejipdivgxzcqszbw |
| haenael-ifia6je8a | 2026-10-12 | ossvejipdivgxzcqszbw |
| haenael-89fwun3m8 | 2026-10-12 | ossvejipdivgxzcqszbw |

**경계가 깔끔하다. 2026-10-09 13:49 배포부터 새 DB 다.** 그 이전 배포는 전부 이전 DB 를 본다.
`wiki/ops/인프라.md` 가 적은 컷오버 날짜(2026-10-09)와 일치한다.

**그래서 무엇이 달라졌나.** 접속 대상 프로젝트 ref 만 바뀌었다. 스키마는 동일하고(위 대조표) 애플리케이션 코드도 동일하다.
**바뀐 것은 접속 대상 프로젝트의 레코드가 0행이라는 점뿐이다.**

## 스키마 대조 (2026-10-12 실측)

두 DB 의 노출 테이블을 같은 방식으로 찔러 응답 코드를 대조했다. **전부 일치한다.**

| 테이블 | 이전 DB | 현재 DB |
|---|---|---|
| goal / member / cashout_request / clover_ledger / notification / report | 200 | 200 |
| goal_public / cheer_public | 200 | 200 |
| cheer | 401 (권한 회수, 설계대로) | 401 |
| welcome_clover / payment_intent / toss_webhook_event / cashout_account | 404 (미노출) | 404 |

**의미.** 스키마가 갈라지지 않았으므로 **변환 없이 그대로 복사**하면 된다.
이것이 "되돌리기"보다 "옮기기"를 추천하는 두 번째 근거다.

## 이전 프로젝트의 소유 계정 (2026-10-12 실측)

회장 질문: "이전 DB는 어디에있던 뭔 DB인데"

**다른 Supabase 계정 소속이다. 현재 로그인된 어느 계정으로도 열리지 않는다.**

- 프로젝트 ref `gmpwrcxpvgylmllasoqy`, API 키 발급 시각 **2026-07-16 01:02**.
  즉 최소 7월 16일부터 10월 9일까지 약 3개월간 이것이 운영 데이터베이스였다.
- 전용 크롬 프로필 10개의 디버깅 포트를 통해 각 세션의 접근 권한을 확인했다.
  Supabase 로그인된 프로필은 4개이고 **4개 전부 이 프로젝트에서
  `You do not have access to this project` 를 반환한다.**

| 포트 | 계정 | 조직 | 이전 프로젝트 접근 |
|---|---|---|---|
| 9333 | j.the.great.investor@gmail.com | haejo-danta (2 projects) | 거부 |
| 9341 | the.edu.devs@gmail.com | (조직 없음) | 거부 |
| 9342 | haenaelge.official@gmail.com | 해낼게 (**1 project**) | 거부 |
| 9348 | code0to1@gmail.com | (1 project) | 거부 |

해낼게 조직에 프로젝트가 **1개뿐**이라는 것이 결정적이다. 현재 운영 프로젝트
`ossvejipdivgxzcqszbw` 가 그 1개이고, 이전 프로젝트는 이 조직에 없다.

**따라서 이전 프로젝트는 위 4개가 아닌 제5의 Supabase 계정이 소유한다.**
그 계정으로 로그인해야 service_role 키를 발급받아 레코드를 읽어올 수 있다.

## 권고 변경: 레코드 복사가 아니라 프로젝트 이전

앞서 공개 뷰만 보고 2행·24행으로 판단해 "레코드 복사"를 권고했다. **그 권고를 철회한다.**

실제로는 `auth.users` 3행과 `cashout_request` 4행, `clover_ledger` 44행이 걸려 있다.
계정 자격증명과 정산 원장이다. 이것을 프로젝트 간에 복사하면

- `auth.users` 를 옮기지 못하면 기존 회원 로그인이 끊긴다. `member.id` 가 이를 참조한다.
- 정산 원장과 환전 신청은 금액 정합이 깨지면 복구가 어렵다.
- 복사 과정에서 대량 개인정보가 중간 경로를 거친다.

반면 **프로젝트 자체를 `해낼게` 조직으로 이전하면 레코드·인증·원장이 그대로 유지된다.**
이전 후 현재 프로젝트에만 적용된 마이그레이션 차분을 이전 프로젝트에 적용하면 된다.

**전제 조건(대시보드 원문).** "To transfer projects, the owner must be a member of both
the source and target organizations." 즉 **postAGI 계정을 `해낼게` 조직 멤버로 초대**하거나
그 반대가 선행돼야 한다.

**선행 권고.** 이전 프로젝트는 백업이 없고 상태가 `Unhealthy` 다. 이전 작업 전에 백업을 확보한다.

## 회장이 정해야 할 것

**무엇을.** 이전 DB 의 데이터를 현재 DB 로 옮길지, 아니면 운영을 이전 DB 로 되돌릴지.

**옮기면.** 새 프로젝트의 최신 스키마(마이그레이션 44개)를 그대로 쓴다. 다만 두 DB 의
스키마가 그사이 갈라졌으면 변환이 필요하고, `auth.users` 를 옮겨야 기존 회원이
그대로 로그인된다. 결제·정산 원장은 금액이 걸린 데이터라 검증이 필요하다.

**되돌리면.** 지금 당장 데이터가 보인다. 대신 10-07 이후 새 프로젝트에만 적용한
마이그레이션과 엣지함수 배포를 이전 DB 에 다시 맞춰야 한다.

**추천: 옮긴다.** 되돌리기는 새 프로젝트에서 한 작업(마이그레이션 44개, 엣지함수 11개,
함수 시크릿 13개)을 버리게 된다. 데이터는 2건·24건으로 작아서 옮기는 쪽이 싸다.

**옮기려면 두 프로젝트의 서버 키가 필요하고, 그건 회장 계정에만 있다.**
현재 로컬 `haenael-ge.env` 의 service_role 키는 **이미 무효**다(`Invalid API key`).

## 곁다리

- 현재 운영 DB 는 레거시 JWT 키를 폐기하고 새 형식(`sb_publishable_`)으로 넘어갔다.
  로컬에 저장된 service_role 키가 그래서 안 먹는다. 새 형식 서버 키를 받아 보관해야 한다.
- 이전 DB 는 아직 레거시 키로 열린다. 데이터를 옮기기 전까지 **삭제하면 안 된다.**
