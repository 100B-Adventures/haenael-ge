# 고쳤다고 말한 것들이 왜 다음 세션에 되살아났나

2026-08-30 · 컨트롤러 Opus 5 · 환전 클로버 잠금(30·27 계약) 슬라이스

## 한 줄 결론

**이 스프린트의 실수 다섯 건은 서로 다른 사건이 아니라 한 병의 다섯 증상이다.
고친 자리에 다시 무너지지 않게 하는 장치를 안 두고 "고쳤다"고 말했다.**
수정 자체는 매번 옳았다. 그 수정이 살아 있는지 묻는 검사가 없었을 뿐이다.

## 무엇이 일어났나

| 건 | 내가 한 말 | 실제 |
|---|---|---|
| 30클로버 신청 거부 | "개정 완료" | 마이그레이션 파일만 있고 운영 DB 미적용. 버그 그대로 살아 있었음 |
| 산출물 정합 검사기 | 2026-08-27 "고침" | 같은 버그가 8-28 재발. 22건 전부 오탐 + 스크립트 사망 |
| 운영 대표 주소 | 2026-08-25 "복구" | 별칭 한 번 옮겼을 뿐. 구조는 그대로라 최신 배포가 또 안 나감 |
| 품질 검증 픽스처 | 통과 중이라 믿음 | 검증 규칙만 강화하고 픽스처를 안 고쳐 조용히 실패 중이었음 |
| CI 차단 원인 | "결제 실패" | 무료 사용량 소진 + 예산 0원. 브라우저로 실화면을 봐야 갈렸음 |

## 왜 이렇게 됐나

### 1. 파일을 쓴 것과 적용된 것을 같은 말로 불렀다

가장 비싼 실수다. 회장이 직접 신고한 버그였고, 수정 SQL 도 정확했고, 로컬
테스트도 통과했다. 그런데 **운영 DB 에 올리는 명령을 아무도 안 쳤다.**

"로컬 테스트 통과"를 완료 근거로 썼다. 이건 대리지표다. 마이그레이션은
파일 존재와 적용 여부가 완전히 별개인데, 그 둘 사이를 확인하는 습관이 없었다.
`supabase migration list --linked` 한 줄이면 42개 중 하나가 비어 있는 게
바로 보였다. 그 한 줄을 스프린트 끝에서야 쳤다.

### 2. 고친 자리에 회귀 테스트를 안 남겼다

산출물 정합 검사기의 문자열 처리 버그는 8월 27일에 이미 한 번 고쳤다.
그런데 8월 28일에 똑같이 되살아났다. 이유는 단순하다. **고친 사실을
붙잡아두는 테스트가 없었다.** 고치고 커밋하면 끝이라고 여겼다.

같은 구조가 품질 검증 픽스처에서도 나왔다. 검증 규칙에 요구사항 셋을
추가하면서 그 규칙으로 채점될 픽스처는 안 고쳤다. 결과적으로 **품질
게이트를 강화한 행위가 품질 게이트를 죽였다.** 강화한 사람도 그걸 몰랐다.

### 3. 증상을 고치고 구조를 안 봤다

운영 대표 주소가 최신 배포를 안 가리키는 문제는 8월 25일에 처음 터졌다.
그때 별칭을 한 번 옮겨서 그날의 증상은 사라졌다. 하지만 **왜 자동으로
안 따라오는지는 안 봤다.** 그래서 사흘 뒤 똑같이 어긋났다.

증상만 고치면 다음에 또 손으로 고쳐야 한다. 손으로 고칠 사람이 그날
없으면 조용히 어긋난 채로 간다. 실제로 그렇게 됐고, 그 사이 회장은
1.0.0 을 보고 있었다.

### 4. 확인할 수 있는 화면을 안 보고 판정했다

CI 차단을 "결제 실패"라고 단정했다. 근거는 API 가 준 문구 하나였는데,
그 문구는 결제 실패와 예산 초과를 **함께** 표현하는 공통 문구였다.
브라우저로 청구 화면을 직접 열자 총액 0원, 무료 2,000분 소진, 예산 0원이
나왔다. 결제는 멀쩡했다.

회장께 "결제가 실패했다"고 보고했으니, 회장은 카드를 확인하러 갔을 것이다.
없는 문제를 찾게 만든 것이다.

### 5. 상류 빈틈이 하류 끝에서 발견됐다

지급 신원·세무정보를 누가 수집하고 어디에 두는지는 기획서에 항목만 있고
설계 계약이 없었다. 이 빈틈은 기획 단계부터 있었는데 **배포 직전 전면
감사에서야 드러났다.** 그래서 파이프라인이 기술설계까지 되돌아갔다.

되돌아간 것 자체는 옳다. 늦게 발견된 것이 문제다.

## 무엇을 바꿨나

| 바꾼 것 | 어디 |
|---|---|
| 산출물 정합 검사기 회귀 테스트 신설 | 하네스 픽스처 스위트 (17건 통과) |
| 죽어 있던 품질 검증 픽스처 되살림 | 신규 요구 3종 반영 |
| 세무 결정을 보류로 명시 등재 | 미결정 원장, 재개 조건 포함 |
| 승인 산출물 핀 37건 실물 최신본 재정렬 | `pipeline-state.core.md` |

## 다음에 안 되풀이하려면

1. **"적용됐다"는 적용된 쪽에서 확인한다.** 마이그레이션은 원격 목록으로,
   배포는 운영 주소 응답으로, 환경변수는 실제 응답값으로. 로컬은 근거가 못 된다.
2. **고칠 때 회귀 검사를 같이 낸다.** 검사 없는 수정은 다음 세션에 증발한다고
   전제한다. 이번 스프린트가 그 전제를 두 번 증명했다.
3. **손으로 한 번 고친 것은 구조를 본다.** 두 번째로 같은 걸 손으로 고치고
   있으면 그건 증상 치료다.
4. **외부 서비스 판정은 콘솔 화면으로 닫는다.** API 문구는 여러 원인을 한
   문장에 담는다.

## 덧붙임: 회고를 쓴 그날 같은 병을 다시 앓았다

위 진단을 쓴 직후 배포를 눌렀다. 실패했다. 그리고 그 실패도 같은 병이었다.

**첫 번째.** 다른 세션이 올려둔 next 업그레이드가 커밋에 섞여 있었는데,
그게 배포를 깨뜨리는지 확인하지 않고 밀었다. 로컬 빌드 통과를 배포 가능의
근거로 썼다. **실패한 지점은 빌드 다음 단계였다.** 위 §1 이 "파일을 쓴 것과
적용된 것을 같은 말로 불렀다"였는데, 이번엔 "로컬에서 된 것과 배포에서 되는
것"을 같은 말로 불렀다. 같은 문장의 다른 판이다.

**두 번째.** 원인을 파보니 Vercel 이 next 버전을 못 읽고 있었다. 프로젝트
Root Directory 가 비어 있는데 `package.json` 은 `web` 아래에 있었다. 넉 달 전
누군가 빌드 명령을 대신 지정해서 **빌드는 돌게 만들었고 설정은 그대로 뒀다.**
증상이 사라졌으니 끝난 줄 알았을 것이다. 그 미설정이 넉 달을 기다렸다가
전혀 다른 이유로 터졌다. 위 §3 이 예고한 그대로다.

## 이번에 증상 대신 구조를 고친 것

같은 말을 세 번 하고 싶지 않아서, 이번엔 손으로 넘기지 않고 뿌리를 뽑았다.

| 증상 | 손으로 넘기는 법 | 실제로 한 것 |
|---|---|---|
| 배포가 출력 단계에서 죽음 | next 를 옛 버전으로 원복 | Root Directory 를 `web` 으로 설정하고 우회 설정을 걷어냄 |
| 운영 버전 표기가 낡음 | 환경변수를 손으로 고침 | `package.json` 을 유일한 진실원으로 삼아 빌드 시각 주입 |
| 대표 주소 보안 헤더 미검증 | 그때그때 눈으로 확인 | QA 스크립트가 보던 redirect 주소를 대표 주소로 교정 |
| 브라우저 콘솔 오류 | CSP 를 열어 통과시킴 | 카카오 링크의 prefetch 를 끔. CSP 는 그대로 |

세 번째 줄이 특히 뼈아프다. **QA 검증 스크립트가 대표 주소가 아니라 그리로
redirect 하는 다른 주소를 보고 있었다.** 그래서 "운영 검증 통과"를 여러 번
보고했는데 대표 주소의 응답 헤더는 한 번도 검증한 적이 없었다. 보안 헤더 누락이
오래 안 잡힌 이유가 이것이다. **검사기가 엉뚱한 곳을 보고 있으면 통과는 통과가
아니다.**

네 번째 줄도 남길 만하다. 배포 직후 콘솔에 새 오류가 떴을 때, CSP 에 카카오
도메인을 추가하면 1분이면 사라졌다. 하지만 그건 보안 정책을 넓혀 증상을 지우는
것이다. 실제 원인은 쓰지도 않는 prefetch 였고 그걸 껐다. **고치는 방향이
둘일 때, 방어를 낮추는 쪽이 대개 더 쉽고 대개 틀렸다.**

## 남은 것

- **환전 폼 캡처.** 시안 대조에 쓰인 실화면이 기능 스위치가 꺼진 상태로 찍혀
  대기 카드만 나온다. 폼과 시안을 맞춰본 적이 아직 없다.
- **대표 주소 자동 승격.** 지금은 배포마다 손으로 옮긴다. 프로젝트 도메인으로
  등록되지 않아서인데, 이걸 안 고치면 §3 의 네 번째 사례가 된다.
- **CI 자동 검증.** 무료 사용량 소진과 예산 0원으로 막혀 있다.
- **총보유 30·지급가능 27 회원의 실제 신청 성공.** 현재 그 상태의 계정이
  0명이라 자연 발생을 기다린다.
