# 해낼게 운영 인증 E2E 요청 원문

## 요청 번호

| 요청번호 | 요청 요지 |
|---|---|
| QA-PROD-AUTH-01 | 운영에서 로그인 세션이 필요한 환전 화면까지 자동 검증한다. |
| QA-PROD-AUTH-02 | 시험용 환전 신청을 운영에 쌓지 않고, 쓰기가 필요하면 즉시 정리되며 실사용자와 구분되게 한다. |
| QA-PROD-AUTH-03 | 시험 계정 자격증명의 저장 위치와 권한을 설계하고 원문을 코드와 문서에 남기지 않는다. |
| QA-PROD-AUTH-04 | 구현 가능한 부분을 실제 운영에서 실행해 관찰 증거를 남긴다. |
| QA-PROD-AUTH-05 | 환전 접수와 알림톡 도착처럼 안전하게 자동화할 수 없는 경로는 미검증 경계를 명시한다. |
| QA-PROD-AUTH-06 | 변경만 남기고 커밋하지 않으며 파일과 줄로 보고한다. |

## Verbatim

> 운영에서 **로그인이 필요한 경로까지** 자동 검증하는 방법을 설계하고 구현하라.
>
> 고려할 것:
> 1. **운영 데이터를 더럽히면 안 된다.** 회장이 명시적으로 제지한 사항이다(기록에 노이즈 생기는거아니야). 시험용 신청을 운영에 쌓지 마라. 읽기 전용 검증이거나, 쓰기가 필요하면 즉시 정리되고 실사용자와 구분되는 방식이어야 한다.
> 2. **자격증명 취급.** 운영 로그인 세션을 어떻게 얻을지가 핵심 난제다. 시험 계정을 쓴다면 그 자격증명을 어디에 어떻게 두는지까지 설계에 포함하라(값은 절대 코드·문서에 원문으로 쓰지 마라. 권한 600 이 규약).
> 3. 실현 불가능하다고 판단되면 **그 이유와 대안**을 내라. 억지로 만들지 마라. 예: 배포 후 운영 DB 조회로 사후 확인하는 방식이 더 안전하다면 그렇게 제안하라.
>
> 완료 조건:
> - 설계 문서(무엇을 어떻게 검증하고 무엇은 못 하는지 경계 명시).
> - 구현 가능한 부분은 구현하고 실제로 돌려 결과를 보여라.
> - 못 하는 부분은 '미검증'으로 명확히 남겨라. '될 것이다' 금지.
> - 커밋하지 마라. 변경만 남기고 파일:줄로 보고.
